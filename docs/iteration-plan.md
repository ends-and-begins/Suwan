## 1. 总体目标与判断标准

**项目愿景：让苏晚成为生活在用户电脑里的数字伙伴。她能记住共同经历，拥有稳定的表达与生活节奏，在独处时学习、创作和回忆，并让这些经历影响下一次交流。**

优先服务一个用户在同一台电脑上长期相处的场景，以现有 Python、asyncio、事件总线、器官和 Tkinter 前端为基础逐步迭代。

产品是否向前推进，主要看四个问题：

1. **记得住吗？** 换一种说法、隔几天、重启后，仍能找回相关的共同经历。
2. **经历会改变她吗？** 用户的偏好、关系变化与历史反馈，能够影响回应和行为。
3. **她的日常有连续性吗？** 主动活动有理由、有过程、有产物，能接着上次继续。
4. **用户愿意每天打开吗？** 交流顺畅、主动程度合适、运行稳定、数据与调用开销可管理。

“数字生命”在本计划中是产品体验目标；“学习”指可保存、可检索、可复用的知识和经验积累。当前迭代不涉及模型权重训练，也不以意识或主观体验作为验收项。

## 4. 阶段 0：把现有项目变成可信的开发起点

执行记录（2026-10-16）：本轮本地可靠性修复和验收已完成。备份 463 文件校验及完整恢复演练一致，原门禁 65 测试通过，修复后 126 测试通过；真实 Tk 控件、REPL 进程、10 次重启与数据恢复通过。LLM/联网/TTS 实际服务、人工自然度评审及长期运行未验证，不以本地结果替代。具体证据和边界见 [round1-report.md](round1-report.md)。

**目标**：明确哪些能力实际可用、哪些存在缺陷，让后续每次改动都能与同一基线比较。

**实施路径**：

1. 记录 Python、依赖、启动方式和数据目录；为复验建立独立的数据目录和备份样本，明确同一数据目录只允许一个实例写入。
2. 执行现有质量门禁和行为对照，记录实际测试数量与失败项；分别验证 REPL 和 GUI。
3. 走通“介绍名字 → 对话 → 创作 → 保存 → 退出 → 重启恢复”的本地流程。
4. 把真实模型、搜索、语音连通性列为独立实测项；先关闭周期生成和自动重试，再按固定少量用例记录供应商、模型、耗时、次数和结果。
5. 排查退出丢状态、异常阻塞、线程读写、慢调用和数据损坏处理；优先修复阻断使用的问题。
6. 对齐 README、架构与历史里程碑的状态表述，建立当前缺陷清单和统一验收场景；先写简短人格约束，供后续记忆和对话场景共同使用。
7. 在分享功能测试前保存样本副本，核实当前读取后删除文件的行为；先用测试目录，不直接消费真实资料。

**方法**：先复现再定位；纯本地、模拟外部响应、真实接口分开验证。自动化测试直接构造无密钥配置或屏蔽环境加载，不把 `Settings.from_env(env={})` 当作隔离保证；模拟适配器并阻断网络出口。时间相关测试沿用 ManualClock，随机决策固定种子。接口慢或不可用时保留已有本地降级路径。

**涉及位置**：`scripts/run_tests.py`、`scripts/parity.py`、`app.py`、`config.py`、`frontends/bridge.py`、`organs/store.py`、`adapters/filestore.py`、现有测试与说明文档。

**交付物**：基线报告、按严重度排序的缺陷表、可复现的运行说明、备份/恢复操作记录、后续共用的场景集与简短人格约束。

**验收标准**：

- 现有门禁全部通过，失败后修复的项目有复验记录，测试数量以本次实际输出为准。
- 独立数据目录中连续完成 10 次启动/退出；已提交保存的名字、记忆和目标不丢失。
- 同一目录的第二个写入实例被明确阻止或以只读方式打开；备份样本可以在空目录恢复并核对关键内容。
- 模拟损坏快照或写入失败时，有可见诊断，原文件保留，并能使用备份恢复。
- 无 API、模拟超时/失败的场景均能继续本地交流；真实接口逐项标明“通过/失败/未验证”。
- GUI 和 REPL 的关键流程有实际操作记录；未验证项列为剩余工作，不标记完成。

**阶段演示**：告诉苏晚名字，聊一段经历，生成一篇作品，关闭后再次打开，找到名字、经历和作品。

## 5. 阶段 1：让苏晚可靠地记住共同经历

执行记录（2026-10-16）：第二版本地范围已完成。固定30场景包含20个改述检索、5个事实更新及5个未知/遗忘/暂停场景；更新和隐私另通过真实运行时保存/重启验证。实现、验收凭据及范围见 [round2-report.md](round2-report.md)，使用和回退见 [memory-v2.md](memory-v2.md)。本地规则检索达到本阶段 Top-3 目标，本轮未接入向量服务，也不将此结果等同模型回答准确率。

**目标**：对话能稳定地使用相关记忆，用户能够查看、纠正和要求忘记信息。

**实施路径**：

1. 区分用户明确事实、共同事件、资料知识、苏晚生成的内容与推测，保留各自来源。
2. 为记忆增加稳定 ID、类型、来源、发生时间、主题及更新关系；给旧数据增加版本化迁移。
3. 将“整句子串匹配”升级为分词/关键词、实体、时间、重要性组合检索，先形成可测的本地方案。
4. 若改述检索仍明显不足，再以同一场景集评估可选的语义检索；比较命中、延迟和新增依赖后决定是否接入。
5. 对明确身份事实采用确定性读取；将随机浮现保留给自主回忆，避免关键事实查询受随机遗忘影响。
6. 处理“我现在改喝茶了”等更新；新事实替代旧事实，冲突未明确时保留不确定性。
7. 增加查看、纠正、删除和暂停新增记忆的最小入口；同步清理相关摘要、派生索引与缓存。
8. 将分享文件改为成功处理后归档，失败可重试；保存原文来源，去重后再形成摘要和记忆。

**方法**：先检索、再组装上下文；事实与模型推测分别存储，只有来源支持的内容进入事实集合。摘要保留源记忆 ID，确保纠错和删除能追溯。抽取或模型调用失败时保留原始事件待处理，不猜测补全。

**涉及位置**：`organs/memory.py`、`organs/identity.py`、`services/chat.py`、`services/share.py`、`services/reflection.py`、`adapters/migrator.py`、`rpc.py`、必要的前端入口。

**交付物**：记忆数据规范、迁移与回退方案、检索接口、记忆管理入口、固定的 30 个验收场景。

**验收标准**：

- 30 个场景包含 20 个改述/跨会话召回、5 个事实更新、5 个未知/删除场景；关键来源进入检索前 3 条的比例在 20 个召回场景中达到 90%。
- 明确姓名与偏好更新、未知事实不冒充已知、删除后不再召回，在相应固定场景中全部通过。
- 重启后上述结果保持；同一迁移重复执行不重复导入，导入失败不损坏原数据。
- 将独白和故事反复总结后，不会把生成内容重新认定为用户说过的事实。

**阶段演示**：先说“我周末喜欢去骑车”，重启后问“休息日我一般做什么”；再纠正为“最近改成游泳了”，下一次使用最新信息。

## 6. 阶段 2：让人格、情绪和关系进入真实互动

**目标**：苏晚的表达保持一致，同时根据当前状态、共同经历与用户偏好作出有依据的调整。

**实施路径**：

1. 写一份简洁人格说明：常见兴趣、表达习惯、对不确定信息的态度、疲倦与关心的表达方式。
2. 区分稳定人格、短期情绪、关系经历和用户交互偏好，明确各自更新条件。
3. 统一对话上下文，纳入相关记忆、关系摘要、情绪、当前活动和用户的主动联系偏好。
4. 用有来源的互动事件更新关系，例如持续讨论、共同完成作品、修复一次误解；降低重复聊天或重复分享带来的机械加分。
5. 让关系影响称呼、话题熟悉度和主动程度；让情绪影响语气与活动选择，同时保持事实回答可靠。
6. 日记提炼“这次经历如何改变我的理解”，保留事实、推测和文学表达的区别。
7. 提供偏好调整入口，例如“少一点主动消息”“回答直接一些”，并在下次运行保持。

**方法**：建立关系与情绪的事件规则，给每次变化保留原因和来源。使用相同输入、不同状态的对照场景检查行为差异；人格一致性与表达自然度由人工按明确量表评阅，规则与状态更新用自动化验证。

**涉及位置**：`organs/identity.py`、`organs/affect.py`、`organs/relation.py`、`organs/drive.py`、`services/chat.py`、`services/monologue.py`、`services/reflection.py`、`assets/`；按需要新增只读上下文组装服务。

**交付物**：人格说明、关系事件规则、统一上下文结构、交互偏好设置、20 个互动对照场景。

**验收标准**：

- 在 20 个场景中检查身份一致、状态一致、相关记忆有据、偏好遵守四项，至少 18 个场景全部满足。
- 用户提出少联系或改变表达偏好后，设置立即生效并在重启后保持。
- 重复同一事件不会重复计分；关键关系变化能够追溯到对应经历。
- 疲倦、低落等状态不会导致固定知识事实变化，也不会用关系数值要求用户持续陪伴。

**阶段演示**：用户曾表示喜欢简洁交流且不喜欢频繁提醒；再次见面时，苏晚简短回应，提及共同话题，并遵守主动消息设置。

## 7. 阶段 3：让主动生活具有意图和连续性

**目标**：主动活动能够解释原因、延续进展并接收反馈；用户交流优先，后台任务的数量和开销可控。

**实施路径**：

1. 在当前加权选择前加入候选活动、触发原因、预期产物和完成条件，保留轻量随机性。
2. 记录跨轮活动状态，例如一篇未完成的诗、一个待探索的问题、上次提出的话题。
3. 按“意图 → 执行 → 检查结果 → 保存 → 反馈”组织活动；区分成功、失败、暂停和待继续。为活动与步骤分配稳定 ID，保存完成记录，使作品写入、目标推进和通知能够按 ID 去重。
4. 引入冷却、主题去重、安静时段、可配置主动频率；将内部活动与对用户的通知分别决策，睡眠和低精力限制昂贵活动。
5. 对用户对话、后台生成、日记和语音统一安排模型调用；用户交互优先，后台任务可暂停或推迟。
6. 记录实际调用次数、实际 token 用量（供应商返回时）、耗时与失败；缺失用量标为未知，不能按请求上限当作实际消耗。
7. 设置日调用数、token 或金额预算；未配置可信价格时用调用/token 上限。发送前持久化预留额度，恢复已用、在途和未知账目；SDK 内部重试纳入计数，无法观测时禁用内部重试并统一管理。预算耗尽后主动任务降级或暂停。
8. 将用户的“这个话题喜欢/不喜欢”作为有边界的后续选择依据，避免单次反馈立即重写长期兴趣。
9. 明确按运行时长触发的维护任务与按本地日历触发的日记/故事，定义重启、跨日和补写语义，并以日期和活动 ID 去重。

**方法**：用小型活动状态机协调流程，规则决定调度约束，模型用于生成候选和内容。统一调用管理服务只负责排队、限额和可取消性，状态仍由对应器官拥有。请求取消后可能仍在供应商执行，记录为在途，保留已分配预算直至结束或进入明确的未知状态，不能假定零消耗。供应商已受理但结果未知时不自动重复请求，不承诺外部调用恰好执行一次。

**涉及位置**：`services/autonomous.py`、`organs/scheduler.py`、`organs/goals.py`、`organs/store.py`、`services/monologue.py`、`adapters/llm.py`、`app.py`、`config.py`；按需要新增调用管理服务。

**交付物**：活动记录规范、可恢复的活动状态、统一调度与预算配置、主动行为策略、模拟长时程报告。

**验收标准**：

- 固定种子模拟 24 小时：外显主动消息不超过配置上限，安静时段内为 0，同一活动结果不重复通知。
- 所有开始执行的活动可查触发原因和最终状态；失败活动不增加成功进度。
- 用户发来消息后，可排队的后台调用停止抢占；暂停后能从已保存阶段继续。
- 用模拟响应验证预算耗尽、超时、取消、重试和重复事件，均不突破配置的调用数及已分配 token 上限。
- 恢复运行时不会把离线期间的每一个定时触发补成外部调用，也不会重复生成同一作品。
- 覆盖“接近预算上限 → 请求中强退 → 重启再请求”和“作品已写入但完成标记未保存时退出”两个故障点；额度不能因重启重置，已保存作品、进度和通知能够按稳定 ID 去重。

**阶段演示**：苏晚因为之前共同讨论的主题开始写诗；用户来聊天时先回应，之后继续作品，并说明这首诗与那次交流的联系。

## 8. 阶段 4：让学习成果可验证、可复用

**目标**：学习产生可追溯的知识与成果，并在后续交流或创作中被使用；目标进度有证据。

**实施路径**：

1. 用用户分享的资料和已允许获取的页面建立知识条目，记录来源、时间和内容范围。
2. 区分“来自资料的知识”“模型已有知识生成的解释”“创作或推测”，避免把生成笔记当作已核实资料。
3. 将学习拆成提出问题、阅读资料、提炼要点、举例、回答检查题、整理疑问。
4. 建立与个人经历分开的知识集合，沿用阶段 1 的来源和检索能力，避免每个重复摘要都成为新的经历。
5. 为目标定义阶段成果，例如“解释概念 → 完成例子 → 在后续问题中使用”，替换按学习/创作次数固定加分的逻辑。
6. 保存作品的主题、来源与版本；让反馈驱动下一版修改，保留修改理由。
7. 对未通过检查或来源不足的内容标记待核实，后续补充资料后可以更新。

**方法**：第一轮限定为“从用户提供的文本资料中理解并应用知识”这一类任务，先在人工准备、有答案的资料集上验证闭环。任务包含新提供的规则或约定，避免只测模型原有知识。题目和评分依据在学习前确定，应用题提前留出；模型自评仅作辅助，关键结论对照资料或可执行结果检查。知识检索、答案引用和目标进度分别验收。

**涉及位置**：`services/autonomous.py`、`services/search.py`、`services/share.py`、`services/reflection.py`、`organs/goals.py`、记忆/知识存储、作品前端；按需要新增知识服务。

**交付物**：知识条目规范、学习流程、证据驱动的目标进度、作品版本记录、10 组固定学习任务。

**验收标准**：

- 10 组任务均包含学习前问题、指定资料、学习后问题和评分依据；至少 8 组学习后达到预先定义的正确性标准，原本答错项单独报告改善率。
- 每组再给一个预留的应用问题；至少 8 组能够检索到来源并正确使用，而不只是重复原句。
- 所有已完成目标都能找到对应成果与检查记录；空笔记、占位模板和失败任务不能推进完成进度。
- 事实型知识能追溯来源；资料冲突和无法确认的结论保持未确认状态。
- 重启后可以继续未完成学习，并复用已保存知识。
- 学习前无法正确回答、学习后答对并通过预留应用题的任务至少有 5 组；若基线已答对，则更换为尚未提供资料的新任务，不能将原有能力计作本轮成长。

**阶段演示**：分享一份摄影资料，苏晚整理曝光知识；之后讨论照片过暗的原因时，能引用资料解释，并据此修改此前的拍摄建议。

## 9. 阶段 5：让日常陪伴体验顺畅

**目标**：用户能够轻松交流、回顾共同经历、控制主动程度，并理解当前运行状态。

**实施路径**：

1. 以对话为主要入口，整合今日活动、未完成事项和最近作品，减少在多个标签页间查找。
2. 将共同经历、苏晚活动、日记和作品组织为可回顾的时间线，明确区分类型和来源。
3. 完善阶段 1 的记忆管理入口，支持搜索、纠错、忘记，以及查看事实更新关系。
4. 完善安静模式、主动频率、音量/朗读、预算和模型设置，并持久化。
5. 展示发送中、等待、失败、重试、取消和本地降级状态；内容生成不阻塞窗口操作。
6. 把“已配置密钥”“服务可连接”“本次调用成功”分开显示，防止状态指示造成误解。
7. 明确窗口关闭、退出程序和后台运行的语义，给出当前采用的行为；提供数据位置和导出入口。
8. 确定对话全文、独白、日记、作品和诊断日志各自的保留范围、保存时机及清理设置；只有实际持久化的内容承诺可长期回顾。

**方法**：先在现有 Tkinter 中完成核心流程，通过实际操作记录发现阻碍；界面结构只围绕任务完成做调整。跨线程状态读取改为运行时提供的一致快照，变更经运行时命令处理，避免前端与核心各存一份业务状态。

**涉及位置**：`frontends/tkapp.py`、`frontends/bridge.py`、`frontends/repl.py`、`app.py`、设置和快照存储。

**交付物**：日常操作流程、整合后的桌面界面、记忆管理和时间线、使用说明、人工可用性记录。

**验收标准**：

- 完成 8 个固定任务：初次启动、介绍偏好、查找经历、纠正记忆、查看作品、调整主动程度、切换模型、退出恢复；每个任务都能在界面内完成。
- 模拟 30 秒慢调用时，窗口仍可切换页面、滚动、修改设置和执行受支持的取消操作。
- 设置重启后保持；记忆、作品与状态显示能反映本次操作结果。
- 降级、网络错误和语音失败能给出明确状态和恢复入口，系统日志不会淹没日常对话。

**阶段演示**：一次完整日常使用：打开、聊近况、回顾上周经历、纠正一条记忆、查看新作品、开启安静模式，然后退出。

## 10. 阶段 6：长期验证与首版交付

**目标**：把可演示的原型推进到能够持续日常使用、数据可恢复的桌面版本。

**实施路径**：

1. 冻结新增功能，集中处理崩溃、状态不一致、数据恢复和明显的交互问题。
2. 先做 ManualClock 加速长时程测试，再做至少 24 小时真实运行，观察队列、任务、内存、文件增长和调用行为。
3. 进行 7 天实际使用，记录有用回忆、记错/漏记、主动打扰、学习复用、失败恢复和调用开销。
4. 验证强制退出、磁盘写入失败、损坏数据、网络断开、供应商不可用、语音失败等场景。
5. 完成备份、恢复、升级迁移和回退演练；记忆删除策略覆盖活动索引及派生摘要，历史备份保留与清理规则写入说明。
6. 在干净环境验证安装与启动方式；交付物不包含开发密钥和个人运行数据。
7. 发布本机可用的首版包、说明、已知限制和验收报告。

**方法**：用阶段 0 固定的场景集做前后对照；规则验证与真实模型输出质量分开统计。自动化验证通过后再做真实使用记录，不把加速模拟等同于真实连续运行。

**涉及位置**：运行时、存储、调度、适配器、前端、测试、启动/打包脚本及交付文档。

**交付物**：首版交付包、完整验收报告、7 天使用记录、备份恢复说明、迁移与回退说明、剩余问题列表。

**验收标准**：

- 全部门禁通过，各阶段验收指标达到约定目标；严重崩溃、无法启动、已保存数据丢失等阻断问题为 0。
- 24 小时运行后任务/队列无无界增长；日志和内容存储按既定上限或保留策略工作。
- 故障演练不会静默覆盖无法读取的原数据，能回到最后有效快照；未完成任务恢复后不产生重复副作用。
- 7 天内需要手工重启才能继续使用的故障为 0；每次主动消息遵守频率和安静设置，超预算外部调用为 0。
- 记忆召回、纠错、偏好遵守、学习复用分别有结果；报告中保留失败案例，不以平均分掩盖数据或控制问题。
- 干净环境按文档完成启动；发布包不含密钥、个人记忆和开发机专用绝对路径。

**阶段演示**：使用交付包从备份恢复苏晚，继续之前的对话和未完成活动，查看一周共同经历与作品，并导出数据。

## 11. 贯穿所有阶段的实施方法

### 11.1 按可验证的小步推进

每个开发任务采用相同顺序：**选一个用户场景 → 定义输入和成功条件 → 改动必要模块 → 验证状态/数据 → 实际演示 → 更新记录**。

每阶段先完成最小可用链路，再扩展质量和覆盖面。阶段验收未通过时，修复当前阻断项后再进入依赖它的阶段。已明确独立的文档和界面准备工作可以并行。

### 11.2 保持状态归属清楚

- 状态由对应器官拥有，服务负责流程，适配器负责外部能力；前端使用快照和命令。
- 纯查询使用明确的只读接口；跨模块变更通过既定事件/请求应答协议处理，并对重复请求给出一致结果。
- 逐步收敛现有直接跨模块修改状态的入口，随当前功能修正，不重新推倒整个架构。
- 生成内容保留来源与类型；事实更新、删除和摘要重建使用相同的记忆 ID 追踪。

### 11.3 将确定性和生成质量分开验证

| 验证层 | 验证内容 | 方法 |
|---|---|---|
| 规则与状态 | 预算、冷却、关系变化、目标进度、纠错删除 | 固定输入、ManualClock、固定随机种子 |
| 数据与集成 | 迁移、重启、恢复、事件链路、任务去重 | 独立临时目录、模拟外部适配器、故障注入 |
| 模型输出 | 事实依据、人格一致、表达自然、学习应用 | 固定资料和场景，记录模型版本，人工按量表评阅 |
| 真实使用 | 是否有帮助、是否打扰、是否愿意继续用 | 操作记录和 7 天日常反馈 |

只为有业务风险或明确验收目标的行为补充测试；文档和简单展示调整用链接、结构与实际展示检查。每阶段保留失败样本，以便后续回归。

### 11.4 管理数据、时间和调用开销

数据格式变化先备份、再迁移、再校验；失败保留原文件。后台任务受用户设置、预算和调度约束。离线时间用于补算状态，重新上线时合并待处理活动，避免集中补发消息和接口调用。

## 12. 阶段成果与执行入口

- **完成阶段 0**：得到可复验的工程基线，能够判断现有能力的真实状态。
- **完成阶段 1–2**：得到具备可靠共同记忆、初步关系反馈的陪伴版本。
- **完成阶段 3–4**：得到有连续日常、能复用知识与成果的成长版本。
- **完成阶段 5–6**：得到经过长期使用验证、可安装和恢复的桌面首版。

阶段 0 的本地可靠性基线已建立。下一轮从阶段 1 的记忆类型、来源、稳定 ID、更新和删除规则开始，继续沿用本轮场景与备份要求。真实服务连接测试作为独立任务记录，具体供应商、模型、耗时与结果验证前均保留“未验证”；不得将本地门禁通过解释为接口可用或人格成长完成。
